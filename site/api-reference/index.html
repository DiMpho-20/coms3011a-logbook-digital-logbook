    API Reference

    This page documents every endpoint exposed by the Digital Logbook backend API. All endpoints are prefixed with /api and return JSON responses.

    Base URL (production): https://digital-logbook-backend-latest.onrender.com/api — a prefix, not an endpoint: request a path under it, such as /api/health.

    Authentication: Most endpoints require a JWT in the Authorization: Bearer <token> header. Obtain one via the POST /api/auth/login endpoint.

    Health & Diagnostics

    GET /api/health

    Returns service health status. No authentication required.

    Response 200: 

    { "status": "ok" }

    GET /api/db-check

    Verifies database connectivity. No authentication required.

    Response 200: 

    { "status": "ok", "message": "Successfully connected to Neon PostgreSQL via Prisma", "time": "2026-09-28T14:00:00.000Z" }

    Authentication (/api/auth)

    POST /api/auth/register

    Create a new user account.

    Field Type Required Notes
    fullName string Yes
    email string Yes Must be a valid email; unique
    password string Yes Min 8 chars, at least one uppercase letter and one digit

    Response 201: 

    { "message": "User registered successfully. Email auto-verified (dev mode).", "user": { "id": "...", "fullName": "...", "email": "..." } }
    Errors: 409 (duplicate email), 400 (validation failure)

    POST /api/auth/verify-email

    Verify a user's email address with the token sent during registration.

    Field Type Required
    token string Yes

    Response 200: { "message": "Email verified successfully. You can now log in." } Errors: 400 (invalid or expired token)

    POST /api/auth/login

    Authenticate and receive a JWT. If 2FA is enabled, returns a flag instead of a token.

    Field Type Required
    email string Yes
    password string Yes

    Response 200 (no 2FA): 

    { "message": "Login successful", "token": "eyJ...", "user": { "id": "...", "fullName": "...", "email": "..." }, "scheduledDeletionAt": null }
    scheduledDeletionAt is an ISO date when the account is inside its 30-day deletion grace period (see DELETE /api/auth/account), otherwise null. Logging in during the grace period does not cancel the deletion. Once the date has passed, the account is erased at the next login attempt, which then fails with 401 like an unknown email.

    Response 200 (2FA enabled): 

    { "requiresTwoFactor": true, "email": "...", "twoFactorToken": "eyJ..." }
    No session token is issued yet. twoFactorToken proves the password step succeeded; it is valid for five minutes and only for POST /api/auth/login/2fa.

    Errors: 401 (wrong password or unknown email — identical message), 403 (unverified account), 429 (too many attempts)

    POST /api/auth/login/2fa

    Complete sign-in after POST /api/auth/login returned requiresTwoFactor. The account is identified by twoFactorToken, not by an email address, so a code alone cannot sign anyone in.

    Field Type Required
    twoFactorToken string Yes — from the login response
    code string Yes — a 6-digit TOTP code, or a recovery code (XXXXX-XXXXX)

    Response 200: 

    { "message": "Login successful", "token": "eyJ...", "user": { "id": "...", "fullName": "...", "email": "..." }, "scheduledDeletionAt": null, "usedRecoveryCode": false, "recoveryCodesRemaining": 10 }
    A recovery code works once. When one is used, usedRecoveryCode is true so the client can tell the user how many remain.

    Errors: 400 (malformed request), 401 (invalid code, or the twoFactorToken has expired — sign in again), 429 (too many attempts)

    POST /api/auth/forgot-password

    Request a password-reset email. Returns the same message regardless of whether the email exists (prevents account enumeration).

    Field Type Required
    email string Yes

    Response 200: 

    { "message": "If account exists, a password reset email has been sent." }

    POST /api/auth/reset-password

    Reset the password using a single-use token from the reset email.

    Field Type Required
    token string Yes
    newPassword string Yes — same rules as registration

    Response 200: { "message": "Password updated successfully. You can now log in." } Errors: 400 (invalid or expired token)

    DELETE /api/auth/account 🔒

    Schedule the authenticated user's account for deletion. Nothing is removed straight away: the account enters a 30-day grace period, ending at midnight 30 days from the request, and a confirmation email is sent. The user can still log in during that time and can cancel with POST /api/auth/account/cancel-deletion. Once the period has ended, the account and all its data (projects, entries, values, tokens) are permanently deleted by the purge job, which runs when the server starts and then hourly, or at the next login attempt if that comes first.

    Calling this again while a deletion is already scheduled keeps the original date and does not send another email.

    Field Type Required
    confirmPassword string Yes

    Response 200: 

    { "message": "Your account will be permanently deleted on Sat Oct 24 2026.", "scheduledDeletionAt": "2026-10-24T00:00:00.000Z" }
    Errors: 400 (missing confirmPassword), 401 (wrong password), 404 (user not found)

    POST /api/auth/account/cancel-deletion 🔒

    Cancel a scheduled account deletion during the grace period. No request body.

    Response 200: { "message": "Account deletion cancelled." } Errors: 400 (no deletion is scheduled), 404 (user not found)

    POST /api/auth/2fa/setup 🔒

    Begin 2FA setup — returns a TOTP secret and QR code data URL. The secret is stored encrypted, and 2FA is not switched on until verify-setup succeeds.

    Response 200: 

    { "secret": "JBSWY3DPEHPK3PXP", "qrCodeUrl": "data:image/png;base64,..." }
    Errors: 400 (2FA already enabled), 404 (user not found), 503 (the server has no TWO_FACTOR_ENCRYPTION_KEY)

    POST /api/auth/2fa/verify-setup 🔒

    Verify the TOTP code from the authenticator app to complete 2FA setup.

    Field Type Required
    token string Yes — 6-digit TOTP code

    Response 200: 

    { "message": "Two-factor authentication enabled successfully", "recoveryCodes": ["ABCDE-12345", "..."] }
    The recovery codes are stored only as digests, so this response is the only time they can be read. The client must show them to the user now.

    Errors: 400 (incorrect code, no setup in progress, or 2FA already enabled)

    POST /api/auth/2fa/disable 🔒

    Disable 2FA. Requires password re-authentication. The secret and all recovery codes are removed.

    Field Type Required
    password string Yes

    Response 200: { "message": "Two-factor authentication disabled" } Errors: 400 (2FA not enabled), 401 (wrong password), 404 (user not found)

    POST /api/auth/2fa/recovery-codes 🔒

    Replace the recovery codes with a new set. Every previous code stops working. Requires the password, so a borrowed session cannot mint itself a way back in.

    Field Type Required
    password string Yes

    Response 200: 

    { "message": "New recovery codes generated. Your previous codes no longer work.", "recoveryCodes": ["ABCDE-12345", "..."] }
    Errors: 400 (2FA not enabled), 401 (wrong password), 404 (user not found)

    GET /api/auth/2fa/status 🔒

    Check whether 2FA is enabled for the authenticated user, and how many recovery codes are left.

    Response 200: 

    { "isTwoFactorEnabled": true, "recoveryCodesRemaining": 8, "recoveryCodeCount": 10 }

    Projects (/api/projects) 🔒

    POST /api/projects

    Create a new project.

    Field Type Required Notes
    name string Yes Unique per user
    description string No

    Response 201: 

    { "id": "...", "name": "...", "description": "...", "status": "ACTIVE" }
    Errors: 409 (duplicate name), 400 (missing name)

    GET /api/projects

    List all projects for the authenticated user.

    Response 200: Array of project objects.

    GET /api/projects/:id

    Get a single project with its entry fields.

    Response 200: 

    { "id": "...", "name": "...", "status": "ACTIVE", "entryFields": [...] }
    Errors: 404 (not found)

    PUT /api/projects/:id

    Update a project's name or description.

    Field Type Required
    name string No
    description string No

    Response 200: Updated project object. Errors: 409 (duplicate name), 404 (not found)

    PATCH /api/projects/:id/status

    Toggle a project between ACTIVE and ARCHIVED.

    Field Type Required
    status string Yes — "ACTIVE" or "ARCHIVED"

    Response 200: Updated project object. Errors: 400 (invalid status), 404 (not found)

    DELETE /api/projects/:id

    Permanently delete a project together with its entry fields, entries, their values and version history, and its tag links. Unlike archiving (PATCH /api/projects/:id/status), this can't be undone — the interface asks for the project's name to be typed first.

    Response 200: { "message": "Project deleted", "deletedEntries": 12 } Errors: 404 (not found, or not the caller's)

    GET /api/projects/time-summaries

    Time totals for every project the caller owns in one request, so the Projects page does not need one request per project. Projects with no entries are included with zero totals.

    Response 200: 

    [
  { "projectId": "…", "totalMinutes": 180, "totalHours": 3, "entryCount": 5, "lastEntryAt": "2026-09-14T…" }
]

    GET /api/projects/:id/time-summary

    Get aggregated time statistics for a project.

    Response 200: 

    { "totalMinutes": 180, "totalHours": 3, "entryCount": 5, "lastEntryAt": "2026-09-14T..." }

    Entry Fields (/api/...) 🔒

    POST /api/projects/:projectId/entry-fields

    Create a custom entry field for a project.

    Field Type Required Notes
    name string Yes
    type string Yes TEXT, NUMBER, DATE, BOOLEAN, TAGS, CHECKLIST, LINK, REFERENCE, COMPUTED
    required boolean No Default false. Always stored as false for COMPUTED, which fills itself in
    formula string COMPUTED only Required for COMPUTED, rejected for every other type. See Computed formulas

    Creating a COMPUTED field also fills in its value on the project's existing entries, and every change to a project's fields saves a new format version.

    Response 201: Created entry field object. Errors: 400 (missing name, unknown type, missing or invalid formula), 404 (project not found)

    Computed formulas

    A formula is arithmetic over other fields of the same project, referenced by id in braces:

    {hours-field-id} * {rate-field-id}
({pay-field-id} + 50) * 1.15
    • Only numbers, + - * /, parentheses and {field-id} references are allowed.
    • A reference must be a NUMBER or another COMPUTED field in the project. Computed fields are always recalculated in dependency order, never read from a previously stored value.
    • A field may not use itself, directly or through a loop of computed fields.
    • A referenced value that an entry left empty counts as 0. A result that is not a finite number (for example, dividing by zero) rejects the entry.
    • The web app lets people write {Field name} and converts names to ids before calling the API. The API itself only accepts ids.

    Field names are unique within a project

    A project cannot have two live fields with the same name. The comparison ignores case and surrounding whitespace, so Hours, hours and Hours are the same name, and both creating and renaming are checked. A field that has been removed is archived rather than deleted, and an archived name is released for reuse.

    The rule is enforced by a partial unique index on (project_id, lower(name)) WHERE archived_at IS NULL, not only by the API check — the API check is a read followed by a write and would race under concurrent requests, so two simultaneous creations of the same name resolve to one 201 and one 409 rather than two fields.

    Duplicates used to be allowed, and the consequence was not cosmetic. A US22 expression such as SUM({Double hours}) is refused as ambiguous, which made the field unusable in statistics, and a US24 automation rule offered two identically-labelled fields the student could not tell apart.

    Errors: 409 (a live field in this project already has that name)

    GET /api/projects/:projectId/entry-fields

    List the project's current entry fields, oldest first. Archived (deleted) fields are left out; they remain in the format version snapshots.

    Response 200: Array of entry field objects. Errors: 404 (project not found)

    GET /api/projects/:projectId/entry-format-versions

    List all format version snapshots for a project.

    Response 200: Array of format version objects.

    PUT /api/entry-fields/:id

    Update an entry field. All body fields are optional.

    Field Type Notes
    name string Cannot be blank
    type string Only while no entry has a value for the field
    required boolean Always false for COMPUTED
    formula string COMPUTED only; same rules as Computed formulas

    When the formula changes, or a field becomes COMPUTED, the stored result is recalculated on every existing entry in the project. So is every computed field that uses this one, directly or indirectly. This happens in the same transaction as the field update, so entries and statistics never mix old and new results. An entry the new formula cannot be worked out for (for example, a division by zero) is left without a value. Renaming a field does not touch stored results.

    Response 200: Updated entry field object. Errors: 400 (blank name, unknown type, invalid formula or loop, formula on a non-computed field), 404 (field not found), 409 (type change on a field that already has values)

    DELETE /api/entry-fields/:id

    Soft-delete (archive) an entry field. Existing entries retain their values; the field is hidden from new entry forms.

    Response 204: No content. Errors: 404 (field not found)

    Entries (/api/...) 🔒

    GET /api/entries

    List entries across every project belonging to the authenticated user, so a page showing several projects needs one request rather than one per project.

    Scoped to the caller: entries are reached by joining through the owning project, so an id belonging to another account returns nothing rather than that account's data.

    Query param Type Default Notes
    projectId string — Restrict to one project. A project the caller does not own yields an empty list, not a 404
    projectStatus string ALL ACTIVE, ARCHIVED or ALL
    from string — ISO date or datetime, inclusive lower bound
    to string — ISO date or datetime, inclusive upper bound
    limit number 200 Capped at 500
    offset number 0 Rows to skip, for paging ("load more")
    archived string exclude exclude, only or include archived entries
    search string — Case-insensitive text matched against the project name, every field value and tag names. Results are ranked by relevance (see below)
    entryTab string all all, week (the last seven days) or overdue (open entries whose due date has passed)
    tags string — Comma-separated tag names; an entry matches if it has any of them
    sort string newest newest or oldest. Ignored while search is set, since results are then ranked by relevance
    filters string — JSON array of custom-field filters, [{ "fieldId": "…", "op": "gt", "value": "2" }]. Every filter must hold

    All the parameters combine: each one narrows the same result set.

    Custom-field filter operations, by field type:

    Field type op
    TEXT contains, equals
    NUMBER equals, gt, lt
    BOOLEAN is_true, is_false
    DATE on, before, after
    TAGS has_tag

    An unknown field, an operation the field's type does not support, or a non-numeric value for a NUMBER filter returns 400.

    from and to filter on COALESCE(entryDate, createdAt) — the date the interface shows. An entry backdated to March counts as March, not as the day it was typed, which is what the timeline and calendar already display.

    Without search, results are ordered by that same date (newest first unless sort=oldest), with the entry id as a tiebreaker so the order is stable between identical dates.

    Relevance ranking. With search, each entry is scored: 3 if the project name matches, plus 3 for each matching text field, 2 for each matching tags field, 1 for each other matching field, and 2 for each matching tag. Results are ordered by score, then newest first.

    Response 200:

    {
  "entries": [
    {
      "id": "…",
      "projectId": "…",
      "durationMinutes": 45,
      "entryDate": null,
      "dueDate": null,
      "values": { "<fieldId>": "…" },
      "status": "OPEN",
      "completedAt": null,
      "tags": ["coursework"],
      "formatVersionId": "…",
      "createdAt": "…",
      "updatedAt": "…"
    }
  ],
  "formats": {
    "<formatVersionId>": { "version": 3, "fields": [ … ] }
  },
  "limit": 200,
  "offset": 0,
  "truncated": false,
  "stats": { "total": 42, "weekCount": 5, "weekMinutes": 310, "overdueCount": 1, "streak": 3 }
}

    stats covers the whole filtered set, not just the page returned: how many entries match, how many and how many minutes fall in the last seven days, how many are overdue, and the current run of consecutive days with an entry.

    Unlike GET /api/projects/:projectId/entries, an entry does not carry its own format.     Backup & Restore (/api/import) 🔒

    POST /api/import

    Restore a JSON backup made by Settings → Export / Import. The whole backup is imported in one database transaction: either every project, field and entry in the file is imported, or nothing is. That means a failed import can simply be retried.

    The body is the backup file itself (up to 10 MB):

    Field Type Required
    format string Yes — "digital-logbook-backup"
    version number Yes — 1
    projects array Yes — each with name, description, status, fields (id, name, type, required, formula) and entries (durationMinutes, entryDate, dueDate, values keyed by the backup's field ids). Optional: the project's id, tags, createdAt, updatedAt; each entry's id, status, completedAt, tags, archived, archivedAt, createdAt, updatedAt
    • Projects, fields and entries get new ids.     Create a rule. name (≤100 chars, unique per project), trigger (ENTRY_CREATED | ENTRY_UPDATED), conditions (1–10, ANDed), action, enabled (optional, default true). See Semantics and deliberate limitations for the condition and action shapes.

    Response 200: the rule. Errors: 404 (rule not found, or not the caller's)

    PATCH /api/projects/:projectId/automation-rules/:id

    Change any subset of name, trigger, conditions, action, enabled. When conditions or action are supplied, the rule is validated as it will be after the edit — swapping only the action can invalidate conditions that were fine, and vice versa.

    Response 200: the updated rule. Errors: 400 (malformed or invalid rule), 404 (rule not found, or not the caller's), 409 (duplicate name)

    DELETE /api/projects/:projectId/automation-rules/:id

    Response 200: { "message": "Rule deleted" } Errors: 404 (rule not found, or not the caller's)

    Semantics and deliberate limitations

    Triggers. ENTRY_CREATED fires on entry creation; ENTRY_UPDATED fires on every later save, including a status-only change through PATCH /entries/:id/status — so "when an entry is marked done" works no matter which endpoint the UI reaches for.

    Conditions are a flat AND list over either an entry attribute (durationMinutes, status) or a project field (fieldId). Comparison operators: EQ, NEQ, GT, GTE, LT, LTE; presence/truth operators: IS_EMPTY, IS_NOT_EMPTY, IS_TRUE, IS_FALSE. Which operators apply is gated by what the condition reads — NUMBER/COMPUTED fields get the comparisons, TEXT/LINK get equality and presence, BOOLEAN gets IS_TRUE/IS_FALSE. DATE, TAGS, CHECKLIST and REFERENCE fields cannot be used in conditions at all: a stored EntryValue holds whatever string passed Date.parse, so two dates meaning the same day could compare unequal, and the story needs no date rules. Numeric parsing follows the same strictness as statistics: "12kg" is not 12, a blank is not 0, and a value that cannot be parsed makes the comparison false rather than coercing it.

    Actions are ADD_TAG, REMOVE_TAG and SET_STATUS only. There is deliberately no action that writes a field value (it would collide with COMPUTED fields and required-field validation), none that sets a date, and none that creates entries — that last would let one rule spawn unbounded entries and would interact badly with offline replay. SET_STATUS maintains completedAt exactly as a manual status change does.

    Ordering and idempotency. Rules run oldest-first; when several rules set the status, the last one wins. Every action is idempotent — ADD_TAG inserts against the entry-tag composite key, REMOVE_TAG is a delete, SET_STATUS skips a no-op write — so the offline queue replaying a capture cannot double-apply a rule.

    No cascades. Each pass evaluates every rule against one snapshot taken before any action runs, and actions write directly rather than re-entering the save handlers, so a rule's action cannot feed another rule's condition — within the same pass or a later one.

    History. toSnapshot() covers tags and status, so what automation did is recorded as a further entry version: the user's save is version n, automation's effect is n+1, visible and revertable in the history UI.

    My Grades (/api/grades) 🔒

    FEAT-009. A student's university modules and the assessments that make up their marks. The API stores and returns exactly what the student entered; every grade figure (secured points, averages, required marks, what-if projections) is worked out in the browser by the grade engine, apps/frontend/src/lib/grades.ts.

    Two levels of weighting. An assessment's weight is its share of its section. A SEMESTER module has one section worth 100%. A FULL_YEAR module has Semester 1 and Semester 2: semester1Weight is Semester 1's share of the module and Semester 2 counts for the rest, so the two always total 100. There is no default split.

    Ownership. Every route needs a signed-in student. Any route naming a :moduleId or :assessmentId only ever finds the caller's own record: another student's id, or a malformed one, is 404.

    A module object: 

    {
  "id": "...", "code": "COMS3011A", "name": "Software Design", "academicYear": 2026,
  "type": "SEMESTER", "semester": 2, "semester1Weight": null, "targetMark": 50,
  "createdAt": "...", "updatedAt": "...",
  "assessments": [ /* assessment objects, in the student's order */ ]
}

    An assessment object: 

    {
  "id": "...", "moduleId": "...", "name": "Midterm", "section": null, "weight": 40,
  "markObtained": 25, "markMax": 40, "markPercent": null, "missed": false,
  "date": "2026-11-15", "dateKind": "TEST", "remind": true, "position": 0, "createdAt": "...", "updatedAt": "..."
}

    • A mark is either markObtained out of markMax, or markPercent, or neither (not marked yet). missed: true counts as 0% and cannot carry a mark.
    • date is a calendar day, YYYY-MM-DD, with no time and so no time zone. dateKind (DUE or TEST) is given exactly when date is.
    • Weights, percentages and marks allow at most two decimal places.
    • There is no status field: it is derived from the mark by the grade engine.

    Response 201: the module object. Errors: 400 (invalid field, or a field that doesn't fit the type), 409 (the same code already exists for that year; repeating a module in a later year is fine)

    GET /api/grades/modules/:moduleId

    Response 200: the module object. Errors: 404

    PATCH /api/grades/modules/:moduleId

    Any of the create fields; at least one. To change type, send the field the new type needs and null for the one it doesn't. A semester module's assessments move into the semester it ran in; a full-year module can only become a semester module while all of its assessments are in one semester.

    Response 200: the updated module object. Errors: 400, 404, 409 (duplicate code, or assessments in both semesters)

    DELETE /api/grades/modules/:moduleId

    Deletes the module and its assessments.

    Response 204. Errors: 404

    POST /api/grades/modules/:moduleId/assessments

    Field Type Required
    name string, up to 120 characters Yes
    weight number, 0–100 (share of its section) Yes
    section 1 or 2 In a FULL_YEAR module only
    markObtained, markMax numbers, markMax above 0 and markObtained no more than it No
    markPercent number, 0–100 No
    missed boolean No
    date YYYY-MM-DD No
    dateKind DUE or TEST With date
    remind boolean: reminders 5 and 2 days before the date No (defaults to true)
    position integer No (defaults to the end)

    Response 201: the assessment object. Errors: 400, 404 (module not found)

    PATCH /api/grades/assessments/:assessmentId

    Any of the create fields; at least one. The mark (markObtained, markMax, markPercent, missed) and the date (date, dateKind) are each replaced as a whole: send any part and the parts left out are cleared, so switching from 25/40 to 62.5% can't leave both behind.

    Response 200: the updated assessment object. Errors: 400, 404

    DELETE /api/grades/assessments/:assessmentId

    Response 204. Errors: 404

    Google Calendar (/api/google-calendar)

    Syncs open entries' due dates into the user's primary Google Calendar using the Google Calendar API (OAuth 2.0, scope calendar.events). Each open, unarchived entry with a due date becomes an all-day event — the same work Open Work lists. The logbook tags its events with private extended properties, so a sync can find them again: it creates new events, updates events whose date or title changed, and removes events for entries that were completed, undated, archived, or deleted. Events the user created themselves are never touched.

    Google access and refresh tokens are stored per user, encrypted with AES-256-GCM (GOOGLE_TOKEN_ENCRYPTION_KEY). They are never returned by the API.

    GET /api/google-calendar/connect 🔒

    Returns the Google consent URL. The URL carries a signed, 10-minute state token bound to the caller, which the callback requires.

    Response 200: 

    { "url": "https://accounts.google.com/o/oauth2/v2/auth?...&state=..." }
    Errors: 503 (Google Calendar is not configured on this server)

    GET /api/google-calendar/callback

    Google redirects the browser here after consent. It is not called by the SPA. The user is identified only from the signed state. On completion the browser is redirected to APP_URL/calendar?calendar=connected, =denied (the user cancelled), or =error.

    Query Notes
    code Authorization code from Google
    state Signed state issued by /connect

    Errors: 400 (missing code or state), 401 (invalid or expired state), 503 (not configured on this server)

    GET /api/google-calendar/status 🔒

    Response 200: 

    { "configured": true, "connected": true, "connectedAt": "2026-09-24T10:00:00.000Z" }

    POST /api/google-calendar/sync 🔒

    Mirrors the caller's open, dated, unarchived entries into Google Calendar. Safe to repeat.

    Response 200: 

    { "message": "Due dates synced to Google Calendar.", "created": 2, "updated": 1, "removed": 0 }
    Errors: 400 (not connected), 409 (access was revoked in the Google account; the connection is removed and the user must reconnect), 502 (Google API failure), 503 (not configured on this server)

    DELETE /api/google-calendar/disconnect 🔒

    Revokes the grant at Google (best effort) and deletes the stored tokens. Events that were already synced remain in the user's calendar.

    Response 200: 

    { "message": "Google Calendar connection removed." }

    Update the editable profile fields. A field left out is not changed; null or "" clears it.

    fullName string Up to 255 characters. Cannot be cleared

    Help assistant (/api/assistant) 🔒

    An in-app helper that answers "how do I…?" questions about Digital Logbook, backed by the Gemini API. It is given a written guide to the app and may suggest one page to open. Only the conversation and the page the user is on are sent to Gemini — no logbook data. Rate-limited per IP (RATE_LIMIT_ASSISTANT_MAX per RATE_LIMIT_ASSISTANT_WINDOW_MINUTES).

    POST /api/assistant/chat 🔒

    Field Type Required Notes
    messages { role: "user" \| "model", text: string }[] Yes The conversation so far, oldest first. Must start and end with a user message; each text is 1–1000 characters; only the last 20 are used
    currentPath string No The page the user is on, e.g. /entries; up to 200 characters, passed on only if it looks like an app path

    Response 200: 

    { "reply": "Open Reminders and press New reminder.", "navigateTo": "/reminders" }
    navigateTo is one of the app's pages (/dashboard, /projects, /entries, /open-work, /stats, /calendar, /board, /reminders, /grades, /profile, /settings) or null.

    Errors: 400 (invalid conversation), 429 (rate limited), 502 (no configured Gemini model could answer), 503 (no GEMINI_API_KEY on this server)

    Error Format

    All error responses use a consistent JSON shape:

    { "error": "Human-readable error message" }
    Status Meaning
    400 Validation error (bad input, missing field, invalid enum)
    401 Authentication failure (missing or invalid JWT, wrong password)
    403 Forbidden (e.g. unverified account trying to log in)
    404 Resource not found — also returned for a resource that belongs to another user, so its existence is not revealed
    409 Conflict (duplicate name or email)
    429 Too many requests — the rate limit on sign-in, sign-up, 2FA or the help assistant was hit; wait and try again
    500 Unexpected server error
    502 An external service failed (Google Calendar, or every Gemini model for the help assistant)
    503 A feature is not configured on this server (the 2FA encryption key, the push keys, Google Calendar or the Gemini key)

    Request bodies that fail Zod validation on the auth routes return { "errors": { "<field>": ["message"] } } instead of a single error string.
