    Testing

    This page documents how the Digital Logbook is tested: our test stack and why we chose it, what is covered by automated tests, the formal user feedback process, our testing policy, and proof of passing runs.

    Test Stack & Why We Chose It

    Tool Role Why
    Vitest 4 Test runner and assertion framework Same engine that powers our frontend build tooling (Vite), so one dependency ecosystem covers the whole monorepo. Fast, ESM-native, and watch-mode works out of the box with TypeScript — no extra transpile config.
    Supertest HTTP-level request helper (backend) Lets tests call the Express app directly (request(app).post(...)) without starting a real server or opening a port. We test the real HTTP layer — routing, middleware, validation, status codes, JSON bodies — not just functions.
    React Testing Library Component testing (frontend) Tests components the way users interact with them — finding elements by placeholder text, role, and label rather than by implementation details like CSS class or component state.
    jsdom Browser environment for frontend tests Provides a lightweight DOM inside Node.js so React components can render, fire events, and validate forms without a real browser.
    The real Express app (src/app.ts) System under test (backend) The app module is exported separately from the server entry point (src/index.ts) precisely so tests can import it without binding port 3000.
    Live PostgreSQL (Neon) Real database (backend) Integration tests run against the actual database the app uses, exercising real Prisma queries, real constraints (unique, cascade deletes), and real SQL aggregation. Mocking Prisma would test our mocks, not our app.
    otplib TOTP code generation in tests The 2FA tests generate genuinely valid time-based codes with the same library the server uses to verify them, so the full TOTP round-trip is tested end-to-end.

    Testing pyramid: the backend has integration tests (API-level, real database) and unit tests (pure functions); the frontend has component tests (rendered React components with jsdom) and unit tests (pure logic like saved-filter persistence).

    How the Tests Work

    Backend API test — a real HTTP request to the real Express app backed by the real database:

    it("PATCH /entries/:id/status marks entry DONE and sets completedAt", async () => {
  const res = await request(app)          // real Express app, no port
    .patch(`/api/entries/${statusEntryId}/status`)
    .set(H)                                // Authorization: Bearer <real JWT>
    .send({ status: "DONE" });

  expect(res.status).toBe(200);
  expect(res.body.status).toBe("DONE");
  expect(res.body.completedAt).not.toBeNull();
});

    Frontend component test — renders the real React component in jsdom and asserts on DOM output:

    it("renders the session-expired banner when the URL has ?expired=1", () => {
  window.history.pushState({}, "", "/login?expired=1");
  renderLoginPage();
  expect(screen.getByText(/session expired/i)).toBeInTheDocument();
});

    Backend unit test — exercises pure functions directly:

    it("verifyToken returns null for a tampered token", () => {
  const token = generateToken("user-1");
  const tampered = token.slice(0, -1) + (token.endsWith("A") ? "B" : "A");
  expect(verifyToken(tampered)).toBeNull();
});

    Shared conventions across test files:

    • Own user per file (backend). Each suite creates its own test user (unique UUID + timestamped email), so suites never collide even though Vitest runs test files in parallel.
    • Setup in beforeAll, cleanup via cascade (backend). Fixed data is created once; afterAll deletes the test user and every foreign key is ON DELETE CASCADE.
    • Sequential within a suite where one test's output feeds the next (the 2FA lifecycle).
    • API modules mocked at the boundary (frontend). Frontend component tests mock ../api so they test the UI layer in isolation from the backend.
    • 15s per-test timeout for backend tests — the database is remote (Neon), so round-trips cost ~500ms each.

    How to Run Them

    # Backend tests (from the repository root)
npm run test --workspace=apps/backend

# Frontend tests
npm run test --workspace=apps/frontend

# Watch mode (re-runs on file changes)
npm run test:watch --workspace=apps/backend
npm run test:watch --workspace=apps/frontend

    Backend prerequisites: a reachable DATABASE_URL in apps/backend/.env and a regenerated Prisma client (npx prisma generate in apps/backend — see Bugs Found By Testing).

    Email behaviour in tests: with no SMTP credentials configured, registration auto-verifies (dev mode) and password-reset emails fail silently — both are caught and logged, and the endpoints still behave correctly. The tests assert the HTTP contract, never the email delivery.

    Coverage

    Coverage is measured with Vitest's V8 provider, configured in apps/backend/vitest.config.ts and in the test.coverage block of apps/frontend/vite.config.ts.

    # Backend coverage (needs the same DATABASE_URL as the ordinary run)
npm run test:coverage --workspace=apps/backend

# Frontend coverage
npm run test:coverage --workspace=apps/frontend

    Each run prints a summary table to the terminal and writes lcov.info to <workspace>/coverage/, which most editors and coverage viewers read directly. The coverage/ directories are gitignored; the numbers belong in CI output and in this document, not in the repository.

    Both suites are configured with include: ["src/**"]. Vitest 4 removed the older coverage.all option, and without naming the sources explicitly a file that no test touches is simply absent from the report rather than counted as zero. Listing them keeps the percentage honest: it is coverage of the codebase, not coverage of the files that happen to have tests. Test files and the frontend's test-setup.ts and main.tsx are excluded, since measuring the tests against themselves says nothing.

    In CI

    .gitea/workflows/deploy.yaml runs test:coverage rather than test for both workspaces on every push to main, master, Alondwe and Dineo. The text reporter puts the coverage table directly into the Actions log, so the numbers can be read from a run without downloading anything, and the two lcov.info files are uploaded as a coverage-lcov artifact.

    The upload step is pinned to actions/upload-artifact@v3 and marked continue-on-error. Version 4 of that action depends on an artifact backend that not every Gitea runner provides, and a runner without artifact storage should not fail an otherwise green build — the coverage table is in the log regardless.

    Coverage on the commit

    Gitea 1.24 has no built-in coverage display of the kind GitLab offers, so the workflow publishes the figure itself. .gitea/scripts/report-coverage.mjs reads the coverage-summary.json each workspace writes and posts three commit statuses through the Gitea API: coverage/backend, coverage/frontend and coverage/combined, each described as a line percentage and linking back to the run that produced it. They appear on the commit in the Gitea UI, so the number is visible per commit with no manual step.

    The combined status is the one the marking rubric is judged on, which is why it is published rather than left for a reader to work out from the other two.

    The script is Node rather than shell because jq and curl are not guaranteed on a self-hosted runner while Node is, setup-node having already run. It never fails the build: a missing summary, a missing token, a rejected request and an unreachable host are all logged and exited cleanly, and the step is additionally marked continue-on-error. Publishing a number is not worth turning a green run red.

    It also appends the same table to $GITHUB_STEP_SUMMARY, which renders on the run page for runners that support summaries and is ignored by those that do not.

    If the statuses do not appear, the log will say why — the likeliest cause is the runner's injected token lacking permission to write statuses, in which case a repository secret holding a token with write access can be passed to the step instead.

    No coverage thresholds are enforced yet. The purpose at this stage is to publish the numbers and watch them move; a threshold set before anyone has seen a baseline is an arbitrary number that either passes trivially or blocks work for no reason. Once a few runs have established where the project actually sits, a floor at or slightly below the current figure is worth adding, so coverage can only go up.

    The CI database link, and the ETIMEDOUT failures

    The backend suites run against the hosted Neon database over the public internet. CI has failed repeatedly with ETIMEDOUT — a transport error, raised before the statement ever reached Postgres — landing on an arbitrary query while everything around it read and wrote to the same database without trouble.

    This section has now been wrong twice, so it records what was ruled out as carefully as what was tried.

    Ruled out by measurement. Capping the worker count cut peak concurrency threefold and the failure did not move, which rules out connection-pool pressure. Other suites complete writes seconds before a failure in the same run, which rules out a cold start of the serverless compute.

    Tried and did not work. The pool was created with a connection string and nothing else, so every pg.Pool default applied, including keepAlive: false. Enabling keepalive looked like the answer — DATABASE_URL points at Neon's -pooler endpoint, which drops connections that go quiet. It did not fix it: the next run went from three failures to eight. keepAlive is kept because it is right for a long-lived pool against a pooler, but it is not the cause. A speculative max: 5 added at the same time was removed again; it had no evidence behind it and the run got slower.

    What the evidence actually showed. In the run of 2026-09-27 every one of the eight failures was a read that timed out: four in loadHistory's findFirst, three in the findUniqueOrThrow that takes the pre-edit snapshot in updateEntry, one in getEntries' findMany. Several surfaced not as an error but as a wrong answer downstream — an entry stuck at version 1, a time summary reading 30 instead of 90 — because the read failed inside a handler that carried on regardless.

    The fix that follows from that. utils/readRetry.ts retries an operation only when both hold: it is one of the eight idempotent reads, and it failed with a transport code (ETIMEDOUT, ECONNRESET, ECONNREFUSED, EPIPE, or Prisma's P1001, P1002, P1017). Up to three attempts, with a growing pause. It is applied to every query through a Prisma client extension in prisma.ts.

    Three things it deliberately never does: retry a write, because one that timed out at the transport may still have landed; retry raw SQL, because $queryRawUnsafe could be anything; and retry an error the database actually returned, so a constraint violation is still raised on the first attempt and cannot be hidden. readRetry.test.ts holds each of those as its own test.

    This is also right beyond CI. A student should not see a 500 because one TCP connection went quiet between two of their queries, and a question asked twice returns the same answer.

    The retry in entriesListing.test.ts predates this and is kept; its setup writes are idempotent by construction, since the user fixture upserts and the entry seed is guarded by a row count.

    If ETIMEDOUT still reaches an assertion after this, the next thing to examine is load rather than connections: the suite runs for eight minutes against a free-tier instance, and automationEngine alone accounts for six of those.

    Testing Policy

    1. Every API endpoint gets tests for the happy path and its error paths (400 validation, 401 auth, 404 missing, 409 conflict). If an endpoint has no error-path test, it isn't done.
    2. Never mock what we're testing at the integration level. No Prisma mocks, no stub auth. The database is real; failures must be real failures. Unit tests for pure functions may use mocks for external dependencies.
    3. Security behaviour is tested as behaviour, not implementation — e.g. we assert that unknown-email and wrong-password logins return byte-identical errors, not that some flag was set.
    4. Tests must clean up after themselves via user-cascade deletion, so the shared database stays usable.
    5. Regression rule: any bug found (see below) gets a test that would have caught it before the fix is considered done.
    6. Tests run in CI before every merge to main — a red suite blocks the merge. The Gitea Actions workflow runs both backend and frontend test suites on every push to protected branches.

    User Feedback Process

    Automated testing checks what the code does; user feedback checks whether it works for real users. Our formal process:

    1. Instrument: a standard SUS (System Usability Scale) questionnaire — 10 fixed Likert items, scored 0–100 — so results are quantifiable and comparable across rounds.
    2. Scenario-based sessions: each tester gets the same set of task scenarios (register → create project → add entry → mark done → view stats/calendar → enable 2FA). We record pass/fail per task and where testers hesitate.
    3. Recruitment: 5–8 testers per round — classmates, other teams, and our client.
    4. Analysis & integration: SUS scores and task failures are reviewed as a team; each actionable finding becomes an issue on the tracker with an assigned fix, and fixed items are reported back in the next round.
    5. Records: each round is logged in docs/user-feedback.md with the raw scores, findings, and the feedback → action → commit trail.

    The first formal round is scheduled for Sprint 2; results will be published on this site.

    Bugs Found By Testing

    Writing these tests surfaced two real issues — this is the regression rule in action:

    1. Stale Prisma client broke every entry-creation test (11 pre-existing failures). The generated client predated the Sprint 2 schema, so any query touching entry_fields.archived_at threw PrismaClientValidationError: Unknown argument archivedAt. Fix: run npx prisma generate after pulling schema changes. Lesson: prisma generate belongs in postinstall/CI.

    2. Concurrent entry-field creation can race on format versioning. Each field create does read-latest-version → insert latest+1. Two parallel creates both read version N and both try to insert N+1; the unique (project_id, version) constraint rejects one, so one field creation fails with 400. Fixed (BUG-001): the version bump now runs in a transaction and retries on a unique-constraint collision, so the loser of the race reads again and takes the next number. entryFieldIntegrity.test.ts creates and deletes fields concurrently and checks every version number is distinct and gapless.
