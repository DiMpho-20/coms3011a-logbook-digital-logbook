    Database Design

    Overview

    The Digital Logbook uses a PostgreSQL database to store users, projects, project entry formats, logbook entries and their history, and the features built on top of them: tags, statistics, dashboards, automation and reminders.

    A key design goal was that different projects need different logbook entry structures (e.g. one project may track "hours worked" and "task completed", while another tracks "description" and "outcome"). Rather than hardcoding a fixed set of columns for logbook entries, we adopted an Entity-Attribute-Value (EAV) pattern using ENTRY_FIELD and ENTRY_VALUE. This trades some query simplicity for the flexibility of letting each project define its own entry format without requiring schema changes.

    We use UUIDs rather than auto-incrementing integers as primary keys to avoid exposing sequential, guessable IDs and to make it easier to merge or migrate data across environments without ID collisions.

    The schema has twenty tables. The diagrams below split them into the core logbook and the features around it; USER, PROJECT and LOGBOOK_ENTRY appear in both.

    Constraints

    • USER.email — Unique. Each email can only register once.
    • PROJECT(user_id, name) — Unique. A student cannot have two projects with the same name.
    • ENTRY_FIELD(project_id, lower(name)) — Unique among fields that are not archived, so a project cannot have two live fields whose names differ only in capitals. Statistics, expressions and automation rules refer to fields by name, so a duplicate would make them ambiguous.
    • ENTRY_VALUE(entry_id, field_id) — Unique. One value per field per entry.
    • ENTRY_FORMAT_VERSION(project_id, version) and ENTRY_VERSION(entry_id, version) — Unique. Version numbers increment per project and per entry.
    • TAG(user_id, name), CUSTOM_STATISTIC(project_id, name), AUTOMATION_RULE(project_id, name) — Unique names within their owner.
    • REMINDER(user_id, rule_key) — Unique, so a rule-generated reminder is created once however often the rules are applied.
    • PUSH_SUBSCRIPTION.endpoint — Unique. An endpoint belongs to one browser; if another user signs in on it, the subscription moves to them.
    • TWO_FACTOR_RECOVERY_CODE(user_id, code_hash) — Unique.
    • All foreign keys use ON DELETE CASCADE for full account erasure, except logbook_entries.format_version_id and logbook_entries.recurrence_rule_id, which use ON DELETE SET NULL — deleting a snapshot or a recurrence rule must not destroy entries.

    Indexes

    Besides the unique constraints above, the schema indexes the columns that common queries filter on: projects.user_id, entry_fields.project_id, logbook_entries by project_id, status, due_date and (project_id, status), entry_values by entry_id and field_id, entry_versions.entry_id, tags.user_id, and user_id on the recovery code, push subscription and Google Calendar tables. Reminders are indexed on (user_id, status, remind_at) for the due-reminder query, recurrence_rules on (enabled, next_occurrence) for the recurrence job, and automation_rules on (project_id, enabled) for the rule runner.

    Main Entities

    User

    Represents a student using the Digital Logbook.

    A user can have multiple projects and can request multiple password resets over time.

    Passwords are stored as a salted hash (password_hash), never as plain text.

    Authentication-related columns:

    • is_email_verified, email_verification_token, email_verification_expiry — email ownership is proven before login is allowed. The token is 32 random bytes, expires after one hour, and only its SHA-256 digest is stored.
    • two_factor_secret, is_two_factor_enabled — optional TOTP two-factor authentication. The secret is encrypted with AES-256-GCM before storage. It is staged at setup time and only becomes active (is_two_factor_enabled = true) after the user proves their authenticator works.
    • scheduled_deletion_at — set when the user deletes their account. The account stays usable for a 30-day grace period and is erased by the hourly purge job, or at the next sign-in attempt, once this date has passed.

    See apps/backend/AUTHENTICATION.md in the repository for the full authentication design.

    Two-Factor Recovery Code

    One of ten single-use codes issued when 2FA is enabled, for signing in without the authenticator device. Only a digest is stored; used_at is set when a code is spent. Regenerating the codes replaces the whole set.

    Project

    Represents a separate project belonging to a student.

    A project can contain multiple entry fields, format versions, and logbook entries. Archiving sets status = ARCHIVED; entries stay editable either way.

    Entry Field

    Defines the structure of a project's logbook entries.

    For example, a project could define fields such as:

    • Description (TEXT)
    • Date (DATE)
    • Hours worked (NUMBER)
    • Task completed (BOOLEAN)

    type is enforced at the application layer when validating ENTRY_VALUE.value, since the value itself is stored as a string to support different field types.

    Sprint 2 extended the field types beyond the basic four:

    Type Meaning
    TAGS A list of short labels
    CHECKLIST A list of checkable items
    LINK A web address (http or https)
    REFERENCE A reference to another project or entry
    COMPUTED A value derived from other fields via formula rather than typed in

    archived_at implements soft retirement: a field dropped from the format stops appearing on new entry forms, but existing values remain readable in old entries. formula is only populated for COMPUTED fields and stores the expression the server evaluates on save.

    Entry Format Version

    An immutable snapshot of a project's entry format, taken whenever the format changes (field added, dropped, renamed, or re-typed).

    This is what keeps historical entries readable: each entry pins the format version that was current when it was created (format_version_id), so later format changes never break old entries. Changing a format creates a new snapshot and carries existing entries forward — filling in what it reasonably can — rather than abandoning them.

    The snapshot itself is stored as JSONB (fields), which keeps the whole field definition set together and queryable.

    Logbook Entry

    Represents a recorded activity within a project.

    An entry stores the date it was recorded (entry_date, user-editable for backdating), the amount of time spent (duration_minutes), an optional deadline (due_date), and its completion state:

    • status — OPEN (work still to do) or DONE.
    • completed_at — timestamp set when the entry is marked done.
    • archived_at — set when the entry is moved to the archive. Archived entries are left out of the default views but not deleted.
    • recurrence_rule_id — the rule that generated the entry, if it recurs.

    Open entries with past due dates surface automatically in the Overdue view and the Open Work page's due-date buckets.

    Entry Value

    Stores the value entered for a particular field of a particular logbook entry.

    This allows different projects to have different entry structures.

    Entry Version

    The history of an entry. A row is written on every create, edit, status change, restore and automated change, and rows are never updated or deleted, so a correction always keeps what it replaced. snapshot holds the whole entry as the API returned it at that moment, field names included, so an old version still reads correctly after the project's fields are renamed or removed. Viewing an entry "as of" a date reads the newest version at or before it; restoring writes a new RESTORED version rather than rewriting history.

    Password Reset

    Stores a password-reset request for a user. Each record contains a unique, time-limited token sent to the user's email, and an expires_at timestamp so that reset links become invalid after a short period. Tokens are single-use: all of a user's reset records are deleted in the same transaction that updates the password. Only a SHA-256 digest of the token is stored, never the token itself. This supports the US00.3 – Reset Password user story defined in the Development Plan.

    Tags

    TAG is a user's own vocabulary of labels, applied to projects through PROJECT_TAG and to entries through ENTRY_TAG. Tags are independent of the per-project entry format, so they work the same on every project.

    Custom Statistic

    US23. A named expression over a project's entries. Only the definition is stored: the value is worked out on every read, so it follows the data instead of freezing the number it had when it was saved.

    Dashboard Layout

    US26. The panels a user chose for their dashboard, in the order they arranged them, one row per user. Keeping it on the server rather than in the browser means the same dashboard appears on every device.

    Automation Rule

    US24. A rule that watches one project's entries and applies an action — add a tag, remove a tag, or set the entry's status — when its conditions hold. Rules are evaluated when an entry is captured or updated, after the save commits, so a broken rule can never cost the user their work.

    conditions and action are stored as JSONB rather than normalised tables: a rule is read whole, written whole, and never queried by its parts, so splitting it would add joins without adding a query. user_id sits alongside project_id (as it does for custom_statistics) — it is redundant, since a project has one owner, but it keeps ownership checks single-column. The @@index(project_id, enabled) is the only index an entry save needs: the runner reads a project's enabled rules and evaluates them in memory against the entry it just loaded. See the "Automation Rules" section of the API reference for the rule language and its deliberate limitations.

    Recurrence Rule

    US27. A stable template for an entry that repeats daily, weekly or monthly. Each occurrence is generated from the template rather than copied from the previous occurrence, so editing or completing one occurrence does not change the pattern. next_occurrence is when the next entry is due; the recurrence job and entry reads both create any that have fallen due.

    Reminders

    US28. A REMINDER is either set by the user (MANUAL) or generated from the user's REMINDER_SETTINGS: entries due soon, overdue entries, entries left untouched for a while (STALE), and a daily prompt when nothing has been logged. rule_key identifies which rule and entry produced a generated reminder, so it is only created once. pushed_at records that the reminder has been sent to the user's devices, so it is never pushed twice. PUSH_SUBSCRIPTION holds one row per browser the user has allowed to receive notifications.

    Google Calendar Connection

    The user's Google OAuth tokens, encrypted at rest, used to mirror entry due dates into their calendar. At most one per user.

    Schema Changes Over Time

    How changes are applied

    The schema is managed with Prisma Migrate. On 2026-09-27 the accumulated migration history was squashed into a single baseline, prisma/migrations/0_init/migration.sql, generated with prisma migrate diff --from-empty --to-schema prisma/schema.prisma --script and verified to reproduce the live schema at that time (a drift diff reported no differences, and deploying it to an empty database created every table). npx prisma migrate deploy applies the baseline and every dated migration after it, so it bootstraps a fresh environment end-to-end. New schema changes are made by editing schema.prisma and running npx prisma migrate dev --name <change>, which adds a dated migration on top of the baseline. The incremental migrations that the baseline replaced remain visible in the git history.

    Deployment

    The database is a managed PostgreSQL instance hosted on Neon (serverless, autoscaling). The backend connects with Prisma's driver adapter using the DATABASE_URL environment variable; connection strings never leave the environment configuration.
