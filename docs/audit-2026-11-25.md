## 4. P0 — broken or misleading today

### P0-1. The frontend suite is no longer green, and it fails by calendar date

`apps/frontend/src/pages/__tests__/CalendarPage.test.tsx:277` asserts a chip is named
`"Due: Hand in report"`. Its fixture is pinned to the **15th of the current month**
(`DAY_KEY = ${MONTH}-15`), while `apps/frontend/src/pages/CalendarPage.tsx:281` labels
any day before today as `"Overdue: ..."`.

The suite therefore passes until the 15th and fails from the 16th onward, every month.
It passed on 11 October; it fails on 25 November. Running the file alone reproduces the
failure, so this is deterministic, not flaky:

```
Test Files  1 failed (1)
     Tests  1 failed | 21 passed (22)
```

**Consequence:** the documented "1 616 / 1 616 tests passing" in `docs/testing.md` is no
longer true, and a red frontend run looks like a regression introduced by whoever runs
it next.

**Fix:** pin the fixture to a day that is always in the future within the current month
(e.g. the last day of the month), or accept either label, or freeze the clock with
`vi.setSystemTime`.

---

### P0-2. GitHub has no CI

There is no `.github/` directory. Every automated check lives in
`.gitea/workflows/deploy.yaml` — which is written for Gitea but already branches on
`github.ref`, so it is a hybrid that neither host runs as-is.

Pushing to GitHub today produces: no typecheck, no lint, no tests, no coverage status,
no deploy. Every other finding in this report is unenforced on GitHub until this exists.

**Fix:** add `.github/workflows/ci.yml` preserving the existing step order — build
`packages/shared` first (both apps resolve it through `dist`), then `prisma generate`,
then typecheck, lint, tests, builds.

---

### P0-3. `VITE_API_URL` is dead configuration

`apps/frontend/.env.production` declares
`VITE_API_URL=https://digital-logbook-backend-latest.onrender.com/api`, but
`apps/frontend/src/api/client.ts:6-8` hardcodes that same URL and never reads the
variable. Pointing a build at a different API therefore requires a source edit; the env
file is decorative.

**Fix:** `baseURL: import.meta.env.DEV ? "/api" : (import.meta.env.VITE_API_URL ?? "<fallback>")`.

## 5. P1 — security and robustness

### What is already strong

Worth recording, because these are usually where student projects fail:

- bcrypt password hashing; password policy of 8+ characters with an uppercase letter and
  a digit (`packages/shared/src/auth.ts`).
- Purpose-scoped JWTs: an OAuth `state` and the `2fa-pending` hand-off token cannot be
  replayed as a session (`apps/backend/src/utils/auth.ts`).
- Two-factor secrets and Google Calendar tokens are AES-256-GCM encrypted at rest;
  enabling 2FA without `TWO_FACTOR_ENCRYPTION_KEY` returns 503 rather than storing plaintext.
- Password-reset, email-verification tokens and 2FA recovery codes are stored as SHA-256
  digests, so a database read cannot complete a reset in flight.
- Login failures are generic ("Invalid email or password") and `forgot-password` responds
  identically whether or not the account exists, so neither endpoint enumerates users.
- `requireAuth` is present on every route that is not deliberately public. The only
  public non-auth routes are the OAuth callback (protected by its signed `state`),
  `/api/health`, the root text route, and `/api/db-check` (see P1-4).
- **No SQL injection.** The four `$queryRawUnsafe` sites
  (`stats.controller.ts`, `expressionEvaluation.ts`) interpolate only whitelisted tokens
  and bind every user-supplied value as a placeholder.
- Rate limiters are per-route with environment-tunable windows, and headers are emitted
  on every auth response.

### P1-1. Sessions cannot be revoked

There is no `/auth/logout` route, no `tokenVersion`, and no denylist. Logging out deletes
the token from `localStorage` and nothing else. A token copied off a shared machine, or
leaked, stays valid for the full `expiresIn: "7d"` with no way to invalidate it.

**Fix:** add `tokenVersion` to `User`, embed it in the JWT, reject a mismatch in
`requireAuth`, and bump it on logout, password change and 2FA changes.

### P1-2. JWT in `localStorage`

`apps/frontend/src/pages/LoginPage.tsx:68` and `:128` write the token to `localStorage`,
and `apps/frontend/src/api/client.ts:16` reads it. Any XSS anywhere in the app yields
permanent account takeover, and P1-1 means it cannot be cut off.

**Fix:** move the session to an `httpOnly`, `SameSite=Lax` cookie with CSRF protection, or
at minimum pair a short-lived access token with a revocable refresh token.

### P1-3. CORS trusts any Cloudflare Pages site

`apps/backend/src/app.ts:33-40` allows `http://localhost:5173`,
`http://127.0.0.1:5174`, one specific Pages host, **and the regex `/^https:\/\/.*\.pages\.dev$/`**,
with `credentials: true`. Any Cloudflare Pages deployment is therefore a permitted
origin, and `credentials` is unnecessary because authentication travels in a Bearer
header, not a cookie.

**Fix:** take the allowlist from an environment variable, drop the wildcard regex, and set
`credentials: false`.

### P1-4. Public `/api/db-check`

`apps/backend/src/app.ts:80-92` exposes an unauthenticated endpoint that opens a database
connection per request and replies `"Successfully connected to Neon PostgreSQL via Prisma"`.
That is a free query for anyone, plus an unnecessary disclosure of the database vendor.

**Fix:** delete the route in production, or guard it with `requireAuth` and return only
`{ status }`.

### P1-5. Raw error text on 500 responses

`apps/backend/src/controllers/stats.controller.ts:123` and `:213` return
`error.message` with status 500. Prisma and Postgres messages can name tables, columns
and SQL text. The other sixteen `error.message` returns are 400s carrying validation
detail, which is appropriate; these two are not.

**Fix:** log the error, return a fixed message with status 500.

### P1-6. Missing baseline HTTP hardening

`app.ts` registers `cors` and `express.json` only: no `helmet` (so no CSP, HSTS,
`X-Content-Type-Options`, `Referrer-Policy`), no global error handler, and no JSON 404
for unmatched `/api/*` — Express returns its default handler, which is HTML and, outside
production, includes a stack trace.

**Fix:** `helmet()`, a trailing `app.use((req, res) => res.status(404).json(...))`, and a
four-argument error handler that logs and returns a generic body.

### P1-7. Background jobs assume a single instance

`apps/backend/src/jobs/pushReminders.ts`, `recurringEntries.ts` and
`purgeDeletedAccounts.ts` all run on an in-process `setInterval` with a boolean
`running` guard. That prevents overlap inside one process only; two Render instances
would both materialise recurring entries and both purge accounts. Push notifications are
the exception — they claim rows via `pushedAt` before sending, which is the correct
pattern and should be copied.

There is also no `SIGTERM` handler, so a redeploy drops in-flight requests instead of
finishing them.

**Fix:** make each job's work claimable in the database (a `processedAt` column or
`SELECT ... FOR UPDATE SKIP LOCKED`), or move them to a scheduler that runs once. Add
`process.on("SIGTERM")` with `server.close()`.

### P1-8. Rate limiting is narrow

`authLimiter` and `assistantLimiter` are the only limiters. Every other authenticated
endpoint — including the import endpoint that accepts a 10 MB body — is unlimited per user.

**Fix:** a generous global limiter on `/api`, with the existing tighter ones layered on
top.

## 6. P2 — performance

The client is in good shape: routes are lazy-split in `App.tsx`, `react-vendor` is
separated in `vite.config.ts`, and the largest built chunks are 169 KB (`index`) and
224 KB (`react-vendor`) out of 1.3 MB total. The server has one clear inefficiency.

### P2-1. Time summary computes an aggregate in JavaScript

`apps/backend/src/controllers/project.controller.ts:147-159` fetches **every entry row**
for the project (selecting only `durationMinutes`) and reduces it in Node. Cost grows
linearly with the student's history for a number Postgres could return in one row.

**Fix:** `prisma.logbookEntry.aggregate({ _sum: { durationMinutes: true }, _count: true, where })`.

### P2-2. Pagination exists on one endpoint only

`GET /entries` correctly implements `limit` (default 200, capped at 500) and `offset`.
`GET /projects`, `GET /me/open-entries`, `GET /reminders` and `GET /saved-filters` return
every matching row. Acceptable at course-project scale; `/me/open-entries` is the one that
will bite first, since open work accumulates faster than anything else.

### P2-3. No logging or request correlation

105 `console.*` calls across the backend, no logger, no request ID, no structured output.
Reconstructing why a specific request failed in production is not currently possible.

**Note on what is *not* a problem:** the Prisma schema is well indexed — `[projectId, status]`
on entries, `[userId, status, remindAt]` on reminders, `[projectId, enabled]` on automation
rules, a partial unique index on entry-field names declared in SQL — and the read-retry
extension is a genuinely good idea. No missing-index or N+1 finding survived review.

## 7. P3 — maintainability

### P3-1. Frontend TypeScript is not strict — and does not need to change to become strict

`apps/frontend/tsconfig.app.json` sets `noUnusedLocals`, `noUnusedParameters` and
`noFallthroughCasesInSwitch`, but never sets `"strict": true`. Running
`tsc -p apps/frontend/tsconfig.app.json --noEmit --strict` returns **0 errors**: the code
already satisfies strict mode.

**Fix:** add `"strict": true`. One line, no code churn, and `noImplicitAny` plus
`strictNullChecks` are locked in for future work. This is the best value-per-minute item
in the report.

### P3-2. Node version is required but not declared

`.nvmrc` says 22, `jsdom@30` requires `^22.22.2`, `eslint@10` requires `^20.19` and
`vitest@4` requires `^20`, but no `package.json` has an `engines` field. On a host whose
default `node` is v18.19.1, `npx eslint` dies with `TypeError: util.styleText is not a
function` — an error that says nothing about the real cause.

**Fix:** `"engines": { "node": ">=22.22.2" }` in the root and both apps.

### P3-4. Eight suppressed effect-dependency warnings

`react-hooks/exhaustive-deps` is disabled in `StatsPage` (three times), `CalendarPage`,
`EntriesPage`, `BoardPage`, `SettingsPage` and `EntryHistoryModal`. Each suppresses the
warning rather than proving the closure is safe, so each is a stale-value bug waiting for
a future edit. Separately, `oxlint` flags `SettingsPage.tsx:635`: a `useMemo` keyed on
`active` whose body never reads `active`.

### P3-5. `.env.example` does not document the preferred email provider

`apps/backend/src/utils/email.ts:17-21` selects `brevo` first (`BREVO_API_KEY`), then
`resend`, then `gmail`, then a dev stub — but `.env.example` documents only Resend and
Gmail. Anyone following the example configures the second-choice provider.

### P3-6. Dockerfile reproducibility

- `RUN npm config set registry https://registry.npmmirror.com` before installing — a
  China-hosted mirror, which is slow or unavailable elsewhere and is an avoidable
  supply-chain hop.
- `npm install` rather than `npm ci`, so the lockfile is not authoritative.
- `packages/shared/package.json` is absent at the first install (only copied later by
  `COPY . .`), so the first install resolves a different workspace graph than the second.
- Runs as root, and declares no `HEALTHCHECK`.

### P3-7. No end-to-end or automated accessibility coverage

Zero Playwright, Cypress, Puppeteer or axe dependencies. All 55 frontend test files run in
jsdom, so nothing has ever exercised the real app in a browser, and nothing asserts
contrast, labels or focus order. Six source files sit under 60 % line coverage
(`AnimatedBackground` 16.8 %, `OnYourRadar` 25 %, `DeadlineReminders` 34.4 %,
`RegisterPage` 38.3 %, `GoogleCalendarSync` 58.5 %, `LandingPage` 48.7 %), and
`packages/shared` has no tests at all despite publishing the Zod schemas both apps rely on.

Uncovered files at 0 %: `apps/backend/src/index.ts`, `jobs/pushReminders.ts`,
`jobs/recurringEntries.ts`, `apps/frontend/src/App.tsx`,
`apps/frontend/src/components/ErrorBoundary.tsx`.

## 9. What this audit could not verify

- **The backend suite was not executed.** `apps/backend/.env` points `DATABASE_URL` at
  `127.0.0.1:55433`, and nothing is listening there. Its 85.16 % figure is read from the
  coverage artifact generated against this commit, not from a run performed today.
- **Backend ESLint was not executed.** The host default `node` is v18.19.1 and ESLint 10
  refuses to run below 20.19 (see P3-2). `oxlint` runs and reports one warning.
- **No browser walkthrough.** This is a static and test-level audit; no feature was
  exercised against running servers, so behaviour that only shows in a browser (layout,
  focus order, real service-worker caching) is out of scope.
- **Production configuration was not inspected.** Whether `JWT_SECRET`,
  `TWO_FACTOR_ENCRYPTION_KEY` and `GOOGLE_TOKEN_ENCRYPTION_KEY` are set on Render is not
  observable from the repository. The code correctly refuses to start or refuses the
  feature when they are missing.
